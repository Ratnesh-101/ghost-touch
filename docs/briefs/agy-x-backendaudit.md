# Lane x-backendaudit: security and robustness audit of the public backend

AUDIT ONLY. You change no code and no tests. You write exactly one file: `docs/reports/audit-backend.md` (create it FIRST as a skeleton and fill it section by section, saving as you go). DO NOT edit `docs/BUILD_LOG.md`. Allowed commands: `backend/.venv/Scripts/python -m pytest backend` (once, to record the baseline), `git status`, `git diff`. Never open `.env*`. The backend is deployed publicly on Render (`https://ghost-touch-api.onrender.com`) and takes uploads from anonymous users, so think like an attacker AND like a student on a bad network.

## Read
`backend/app/main.py`, `backend/app/ask.py`, `backend/app/raw_mode.py`, `backend/app/graphs/`, `backend/app/vision/*.py`, `backend/app/validate.py` (read only), `backend/pyproject.toml`, `render.yaml`, `docs/DEPLOY.md`, and the backend tests (to see what is already covered).

## Audit (for each item: PASS, FAIL or CONCERN with file:line, the concrete failure scenario, a minimal fix)
1. Upload handling on `POST /api/v1/scene` and any other upload route: is there a maximum body size enforced BEFORE the whole file is read into memory? Content-type vs magic-bytes validation? What happens with a 40 MB file, a zero-byte file, a non-image with an image content type, a truncated JPEG, a PNG with huge pixel dimensions (decompression bomb) when `raw_mode.py` decodes it with OpenCV, an animated or multi-frame image, an EXIF-rotated photo?
2. Resource exhaustion: no rate limiting or concurrency cap? What does a burst of 50 simultaneous uploads do on a free 512 MB instance (the image is held in memory, then decoded, then base64-encoded for the provider)? Are provider calls cancelled when the client disconnects? Are timeouts enforced end to end?
3. Prompt injection: the diagram image and the scene `facts` come from users and are sent to LLMs (`/scene` extraction, `/ask`, `/validate`). Can text inside an image or inside submitted scene JSON override the system prompt in `/ask`, make it leak the prompt, or answer outside the diagram? Is the model output ever executed or trusted without validation? Is scene JSON posted to `/ask` and `/validate` size-limited and schema-validated (number of points, string lengths, nesting)?
4. Secrets and logging: can an error response, a log line or an exception message contain an API key, an Authorization header or a provider URL with a key? (Tests exist for the 401 case; check the other paths.) Is the uploaded image or its content ever logged or cached on disk? Is the scene cache keyed by image hash safe (collisions, unbounded growth, memory limit, eviction)?
5. CORS and headers: how `ALLOWED_ORIGINS` is parsed (wildcards, trailing slashes, `null`), whether credentials are allowed, response headers (`X-Content-Type-Options`, cache headers on `/health` and JSON), and whether `/docs` and `/openapi.json` are exposed in production.
6. Robustness for real users: behaviour on a provider returning non-JSON, an empty body, or a very large JSON; the Raw Mode fallback when OpenCV finds no contours or too many; error responses are always JSON with a useful `reason`; behaviour when all providers are unconfigured.
7. Dependencies: list the pinned versions in `pyproject.toml`, anything unpinned, and anything known to be end-of-life; note that `pip-audit` found no issue in the app packages on 2026-11-06 (only the venv's own setuptools, since upgraded).
8. Deployment config: `render.yaml` settings that could be wrong (health check path, plan, auto-deploy branch, env var names matching the code, `PORT` handling), and anything in `docs/DEPLOY.md` that no longer matches the code.

## Output
Start with a one-paragraph summary, then a table of findings ordered by severity (CRITICAL, HIGH, MEDIUM, LOW): ID, file:line, problem, scenario, suggested fix. End with "the five fixes to make first" and a list of things that look good. Only report what you can justify from the code; mark guesses "(unverified)".
